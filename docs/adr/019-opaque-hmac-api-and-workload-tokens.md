# ADR-019: Opaque HMAC API and workload tokens

- Status: Accepted
- Date: 2026-08-21
- Scope: EPIC-501

## Context

AMESH needs scoped API credentials, one-time token disclosure, bounded rotation overlap, immediate
revocation, short-lived workload exchange and independent rate limits. PostgreSQL must remain
authoritative in the on-premises topology.

Self-contained JWTs reduce validation reads but make immediate revocation, per-token rate limits and
last-used evidence depend on an additional revocation authority. API tokens are generated by AMESH
and have 256 bits of randomness, so they do not need password-strengthening hashes intended for
low-entropy user secrets.

## Decision

1. Generate opaque bearer secrets with Python `secrets.token_urlsafe(32)`.
2. Persist only HMAC-SHA-256 digests keyed by an externally supplied token pepper. Compare digests
   with `hmac.compare_digest`.
3. Put a UUIDv7 token identifier in the non-secret token prefix so PostgreSQL can load exactly one
   digest without scanning. The secret portion is returned only by issue/rotate/exchange responses.
4. Validate status, principal credential version, scope, audience, expiry and quota in one PostgreSQL
   transaction before recording successful use.
5. Rotation creates a new token and marks the old token superseded with a bounded overlap deadline.
   Revocation and principal-wide credential-version increments take effect on the next request.
6. Workload exchange issues a derived opaque token for at most one hour with scopes no broader than
   its parent and a distinct audience.
7. Current and previous peppers may be configured during a deployment rotation; new tokens use only
   the current pepper. No application image rebuild is required.
8. Bearer tokens are accepted only in the `Authorization` header and require TLS outside local
   development.

## Consequences

- PostgreSQL remains the only credential validation and revocation authority.
- No JWT/PASETO or password-hashing dependency is added.
- Validation performs one authoritative database transaction per bearer request.
- Interactive user login, passwords and browser sessions remain EPIC-403 work.
