# ADR-025: Incremental versioned API contract

Status: accepted

Context: AMESH already exposes a useful `/api/v1` flow, execution, backfill and governance surface, but collection behavior is inconsistent and execution creation waits for the entire workflow to finish. The deployed control room therefore cannot launch work and observe a durable `RUNNING` state. EPIC-400 also names file, key-value and plugin resources whose authoritative lifecycle owners remain outside the current v0.2 release profile.

Decision: keep `/api/v1` backward compatible and complete it incrementally around shared typed request and response contracts. Existing synchronous execution creation remains the default; clients request durable asynchronous launch with `Prefer: respond-async`, receiving HTTP 202 after the execution and task plan commit, while AMESH runs the same executor after the response. Collection endpoints retain their existing full-resource array by default and accept common cursor, filter, stable-sort and top-level field-selection parameters when requested, with cursor state in response headers. State-changing collection operations use `Idempotency-Key`; bounded bulk operations commit each item independently and return one result per item. Errors use an RFC 7807-compatible envelope that retains the existing `detail` field. Large logs, imports, exports and artifacts use streaming responses or uploads. Generated OpenAPI remains the source contract and a repository compatibility check rejects removals from the committed baseline.

The v0.2 API profile covers the authoritative resources implemented in this release: flows and revisions, executions and task runs, triggers, backfills, tenants/namespaces, authorization principals/roles/bindings, credentials, workers, service topology and reconciliation. Namespace-file, key-value, secret-provider and installable-plugin lifecycle endpoints remain explicitly deferred to EPIC-207, EPIC-506 and EPIC-300/301; EPIC-400 does not create placeholder persistence for them.

Consequences: current CLI and frontend callers keep working, while the next frontend epics can launch and watch real executions. A process can fail after the 202 response, so PostgreSQL remains authoritative and the existing executor recovery role must converge the persisted `RUNNING` execution after its configured grace. Partial bulk success is explicit rather than rolled back across unrelated items. A later incompatible representation requires a new API major version and a published overlap window rather than changing `/api/v1` in place.

Build-versus-buy review: FastAPI's built-in `BackgroundTasks` and streaming responses cover post-response execution and incremental response bodies without another runtime dependency. A pagination framework was rejected for this release because its page-envelope response would break the existing array contract. `oasdiff` is the preferred mature compatibility engine for hosted CI, but adding a Go binary to the Python development environment is deferred; the repository check implements the narrower v0.2 guarantee that published paths, methods and response schemas are not removed.
